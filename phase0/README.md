## v1.3 이 실패한 진짜 이유 — 진단 정정

v1.3 명령서는 원인을 "KRX Open API 이용신청 미승인"이라고 적었다. **틀렸다.**

1. KRX 가 **2025-12-27 부로 정보데이터시스템을 회원제 "KRX Data Marketplace" 로 전면
   개편**했다. 로그인이 필수가 되었고 응답 구조가 바뀌었다.
2. pykrx 1.2.8 은 `from pykrx import stock` 하는 순간 `website/comm/webio.py:12` 에서
   `build_krx_session()` 을 실행한다. 그 함수가 부르는 `login_krx()` 는 응답을
   `resp.json()` 으로 파싱하는데 **try/except 가 없다**(`website/comm/auth.py:153`).
   개편으로 로그인 응답이 JSON 이 아니게 되자 `JSONDecodeError: Expecting value: line 13
   column 1 (char 25)` 가 **import 시점에** 그대로 터졌다.
3. 즉 **자격증명이 없어서가 아니라, 자격증명을 넣고 시도한 로그인 자체가 KRX 쪽 변경으로
   실패한 것**이다. v1.3 은 이 실패를 흡수하고 "무자격 재시도"로 넘어가면서 문제를 감췄다.

**KRX ID/PW 와 KRX Open API 인증키는 별개다.**

| 항목 | 정체 | 필요한 절차 |
|---|---|---|
| KRX ID/PW | Data Marketplace 회원 로그인 | 무료 회원가입만. 이용신청 불필요 |
| KRX Open API 인증키 | 별도 서비스 | 키 발급 + **엔드포인트별 이용승인** |

v1.4 는 Open API 승인을 기다리지 않는다. ID/PW 경로(Plan A·B)를 살리고, 그것도 막히면
KRX 에 전혀 의존하지 않는 Plan C 로 내려간다.

## §2 시장 데이터 소스 — 3단 사다리

`Plan A → B → C` 순서로 시도하고, **하나가 성공하면 나머지는 건너뛴다.** 각 단계의 성패와
사유 원문은 `reports/diag_market_source.json` 에 남는다 — 이번 실행의 핵심 진단물이다.

### Plan A — pykrx 최신화

`pip show pykrx` → `pip install --upgrade pykrx` → 버전 재출력 → 카나리
`get_market_cap_by_ticker("20250630", market="ALL")`. 100종목 이상이면 성공.

커널 재시작 대신, **자격증명을 `os.environ` 에 넣은 뒤** `sys.modules` 에서 pykrx 를
걷어내고 다시 import 한다. `build_krx_session()` 이 `os.getenv("KRX_ID")` 를 **기본
인자값으로** 읽기 때문에 이 순서가 결과를 바꾼다(v1.3 의 `KRX_ENV_TOO_LATE` 경고 지점).

> 참고: 이 문서를 쓰는 시점의 PyPI 최신은 **1.2.8** 이고, 그게 바로 깨진 버전이다.
> 업그레이드해도 버전이 그대로일 가능성이 높다 — 그래서 성패 판정은 버전이 아니라
> **카나리 응답**이 한다. 버전 변화 유무는 진단물에 그대로 기록된다.

### Plan B — 마켓플레이스 세션 직접 구성

**추측으로 엔드포인트를 만들지 않는다(`P0_NO_URL_GUESSING`).** 순서는 이렇다:

1. **설치된 pykrx 소스를 `ast` 로 판독**한다. 로그인 URL·payload 키·ID/PW 키·성공코드·
   중복로그인 재전송 규칙·조회 URL·`bld`·파라미터 이름·응답 키·기본 헤더를 전부 코드에서
   읽고, **파일:줄번호까지** 진단물에 남긴다.
2. 그 URL 로 **로그인 응답 원문을 덤프**한다 → `reports/diag_krx_login_response.txt`
   (`status_code` · `headers` · `text[:2000]`). 로그인 페이지인지 차단 안내인지 점검
   공지인지 눈으로 확인할 수 있어야 한다.
3. `requests.Session()` 으로 워밍업 GET → 로그인 POST → 쿠키 유지 → 전종목시세 조회.
   `User-Agent` 와 `Referer` 도 소스에서 읽은 값을 쓴다.
4. 로그인 세션이 실패하면 **비로그인 세션으로 한 번 더** 본다. 이건 추측이 아니라 pykrx
   자신이 취하는 폴백 경로다(`webio.py` 의 `Get/Post` 는 세션이 없으면 익명
   `requests.Session()` 으로 조회한다).

**동시성 금지.** KRX 계열 호출은 락으로 직렬화하고 요청 간 최소 1초를 강제한다 —
주석이 아니라 구조로 막았다(`SerialGate`).

*(실제 pykrx 1.2.8 에 대해 판독이 동작함을 검증했다: 로그인 `MDCCOMS001D1.cmd`,
성공코드 `CD001`, ID 키 `mbrId`, 조회 `getJsonData.cmd`,
`bld=dbms/MDC/STAT/standard/MDCSTAT01501`, 응답 키 `OutBlock_1`.)*

### Plan C — KRX 없이 시총 자체 계산 (최종 폴백)

`시가총액 = 발행주식총수 × 종가`. 이미 작동하는 DART 키만 쓴다.

| 구성요소 | 소스 |
|---|---|
| 발행주식총수 | DART 주식총수 현황 (`stockTotqySttus`) — 분기별 제공이라 PIT 성립 |
| 종가 | FinanceDataReader 개별 종목 시계열 → `cache/raw/px/{ticker}/{year}.parquet` 영구 캐시 |
| 종목 목록 | DART corpCode (파싱 결과 캐시) |
| 시장구분 | DART 응답의 `corp_cls` (Y/K/N) — KONEX 제외에 쓴다 |

**발행주식총수 필드 선택이 이 Plan 의 정확도를 결정한다.** DART 는 이름이 비슷한 필드를
여러 개 준다:

| 필드 | 의미 | 사용 |
|---|---|---|
| `istc_totqy` | 발행주식의 총수 | ✅ **1순위** |
| `isu_stock_totqy` | 발행할 주식의 총수(수권주식수) | ❌ 실제 발행량이 아니다 |
| `now_to_isu_stock_totqy` | 현재까지 발행한 누적 | ❌ 감소분이 안 빠져 있다 |
| `distb_stock_co` | 유통주식수(= 발행 − 자기주식) | 1순위가 응답에 없을 때만, 경고와 함께 |

- **보통주만** 사용한다(`se` 에 '보통' 포함, '우선' 제외, '합계'·'계' 제외).
  보통주 행이 없으면 그 종목은 결측으로 남긴다 — 추정하지 않는다.
- **자기주식은 차감하지 않는다.** KRX 공식 시가총액이 '상장주식수 × 종가'로 자기주식을
  포함하기 때문이다. 목적이 KRX 실측 순위와의 정합이므로 KRX 정의를 따르는 쪽이 순위
  보존성이 높다. 자기주식수 합계는 별도로 기록해 두어 나중에 차감본을 만들 수 있다.
- 거래일 판정은 달력이 아니라 **그 날 실제 체결이 있었는가**로 한다.
- 스냅샷일에 체결이 없으면 10일 내 직전 종가까지만 인정하고, 사용 건수와 최대 경과일을
  기록한다. 그 밖은 결측이다.

**교차검증(필수).** Plan C 로 만든 S4 순위를 `local_cache` 의 S4 실측 시총과 비교해
**스피어만 순위상관**을 산출한다. 0.95 미만이면 "Plan C 를 신뢰할 수 없다"를 판정표와
요약에 명시한다(수치는 그대로 산출한다). 하위 1,000종목 **집합 일치율**도 함께 낸다 —
이번 용도가 순위 컷이라서 그 컷의 재현성이 상관계수보다 직접적인 증거다.

> **필수 한계 표기.** Plan C 의 시가총액은 KRX 공식 시총이 아니라 재구성값이다. 절대
> 수준은 부정확할 수 있다. 이번 용도는 시총 하위 1,000종목이라는 **순위 컷**이므로 순위
> 보존성만 있으면 목적을 달성하지만, **이 수치를 다른 목적에 재사용해서는 안 된다.**

**Plan C 채택 시 4개 스냅샷 전부를 Plan C 로 만든다.** S4 에 KRX 실측 캐시가 있어도
유니버스 구성에는 쓰지 않는다 — 스냅샷마다 시총 소스가 다르면 그 차이 자체가 S3→S4
전이에서 가짜 신호로 보이기 때문이다. 실측 캐시는 교차검증의 기준값으로만 쓴다.

**호출량 주의.** 주식총수는 (종목 × 스냅샷 4개)라서 콜드런에서는 임원현황(~11,078건)보다
크다. 그래서 Plan C 는 수집 전에 예상 호출량을 따로 계산해 보고하고, 5,000건을 넘으면
`P0_CACHE_FIRST` 로 멈춘다. 여러 날에 걸쳐 완주하게 되며 캐시는 전부 이어받는다.

### 3단 모두 실패하면

4개 스냅샷 전부 `UNVERIFIED(NO_MARKET_SOURCE)`. **임원현황 수집에 진입하지 않는다**

## §3 DART 연결 진단 — 벌크 전 필수

v1.3 은 로컬 Windows 에서 31콜이 전부 `net_error` 로 죽고 서킷브레이커에 걸렸다. 같은
코드가 v1.2(Colab)에서는 12,165콜을 정상 처리했다. **벌크에 들어가기 전에 원인을
확정한다** — 단일 카나리 1콜로 예외 타입 전체 이름·메시지 전문·HTTP 상태코드·응답 본문
앞 500자를 전부 출력하고 분류한다. 결과는 `reports/diag_dart_preflight.json`.

| 예외 유형 | 원인 | 조치 | 코드로 해결 |
|---|---|---|---|
| `SSLError` / `CertificateError` | 사내망 SSL 인터셉트 | 회사 루트 인증서를 `REQUESTS_CA_BUNDLE` 에 지정 | 가능 |
| `ProxyError` | 프록시 미설정 | `HTTP_PROXY`/`HTTPS_PROXY` 설정 | 가능 |
| `ReadTimeout`/`ConnectTimeout` | 타임아웃 과소 | 30초로 상향(이미 적용) | 가능 |
| DNS 실패 | 이름 해석 불가 | 망 문제 | **불가 → 보고 후 중단** |
| `ConnectionError`(거부) | 방화벽 차단 | 망 문제 | **불가 → 보고 후 중단** |
| HTTP 200 + 정상 JSON | 일시적 문제였음 | 그대로 진행 | — |

`requests` 의 예외 계층에서 `ProxyError`·`SSLError`·`ConnectTimeout` 은 전부
`ConnectionError` 의 하위 클래스다. 구체적인 것부터 훑지 않으면 SSL 인터셉트가 방화벽으로
오분류되고, 그러면 사용자는 고칠 수 있는 문제를 "망 문제"로 포기한다. 분류기는 MRO 전체를
보고, 이름이 일반적일 때는 **메시지 본문의 증거**(`certificate verify failed` 등)를
우선한다.

**`verify=False` 는 쓰지 않는다(`P0_NO_VERIFY_FALSE`).** 선언으로 끝내지 않고 실행 시
자기 소스를 읽어 검사하며, 소스를 못 읽으면 통과로 위장하지 않고 `UNCHECKABLE` 로 표기한다.

'코드로 해결 불가'로 분류되면 임원현황 수집에 진입하지 않고, **캐시된 분량으로 할 수 있는
것만** 하고 판정표를 낸다(§3.4).

## PIT 정합성 — as_of 는 실행일이 아니다

**관측시점 정렬(A)** 을 채택했다. `as_of` = 해당 보고서의 법정 제출기한.

| 스냅샷 | 기준일 | 보고서 | as_of |
|---|---|---|---|
| S1 | 2025-06-30 | 2025/11012 반기 | 2025-08-14 |
| S2 | 2025-09-30 | 2025/11014 3분기 | 2025-11-14 |
| S3 | 2025-12-31 → **2025-12-30**(휴장일 스냅) | 2025/11011 사업 | 2026-03-31 |
| S4 | 2026-03-31 | 2026/11013 1분기 | 2026-05-15 |

이 값들은 코드에 FROZEN 되어 있고 실행 시 `결산기준일 + 45일(분기·반기) / 90일(사업)`
계산과 대조한다. 어긋나면 실행되지 않는다.

**캐시는 API 원본 응답을 저장하고, PIT 필터는 읽은 뒤에 건다.** 그래서 `as_of` 가 달라져도
기존 캐시는 전부 재사용 가능하다. 필터 후 최종접수일이 `as_of` 를 넘으면 그 자리에서
예외를 던진다. 스냅샷별 PIT 폐기 건수(룩어헤드/접수번호불량 구분)를 로그와
`diag_pit_dropped_delta.csv` 에 출력한다 — **어떤 스냅샷이든 룩어헤드 폐기가 0건이면
필터가 안 걸린 것이므로 경고하고 성공조건 ①을 미충족으로 기록한다.**

## 측정 내용

- **노드** = 해당 스냅샷 거래일의 시총>0 상장사 전체 (KONEX 제외)
- **엣지** = (성명, 출생년월) 동일 인물이 두 종목에 동시 임원 등재
  - 출생년월 결측 레코드는 엣지 생성에서 **제외**(보간하지 않음)
- **측정 대상** = 각 스냅샷의 시총 **하위 1,000종목**
- **상대 노드가 측정 대상 밖이어도 엣지는 유지** — v1.2 실측에서 외부 링크가 전체의 77%였다
- **전이** S1→S2, S2→S3, S3→S4 각각의 하위 1,000종목 교집합에 대해
  `edge_born` / `edge_died` 를 **분리 산출. 절대 합산하지 않는다.**
  양끝 노드가 두 스냅샷 모두에 상장된 경우만 센 보조 수치도 함께 낸다.

### 판정 게이트

| 게이트 | 기준 | 임계 |
|---|---|---|
| AΔ-1 | 분기당 `edge_born ≥ 1` 인 종목 비율 (전이 평균) | ≥ 0.05 |
| AΔ-2 | 분기당 전체 `edge_born` 총건수 중앙값 | ≥ 50 |
| AΔ-3 | 4개 스냅샷 모두 그래프 구성 성공 | 4/4 |

> **AΔ-1=0.05, AΔ-2=50, A-5=600 은 경험적 근거 없이 설정된 임계값이다.** 게이트 미달을
> "전략 불가"로 읽어서는 안 된다. 실행 중 임계 변경은 금지되어 있으며, 임계값 SHA-256 이
> 코드에 고정되어 있어 바꾸면 실행이 중단된다(`P0_NO_THRESHOLD_EDIT`). v1.3 과 동일한
> 값·동일한 해시다.

### 성공 조건 (게이트 통과 여부와 무관)

1. 4개 스냅샷 각각 PIT 폐기 건수 ≠ 0 이고 최종접수일 ≤ `as_of`
2. 전이 3개의 `edge_born` / `edge_died` 산출

**수치가 낮게 나와도 성공이다.** 낮다는 사실을 정확히 아는 것이 이 단계의 목적이다.
부분 성공도 기록한다 — 3단 계획 중 어느 것이 왜 실패했는지가 명확히 남으면 그것만으로도
다음 실행의 출발점이 된다.

## 적대적 리뷰에서 고친 것

작성 후 독립 리뷰어 4명(사다리·DART·측정·흐름)에게 결함을 찾게 하고, 제기된 22건을 각각
반증 담당자에게 넘겨 확인했다. 그 과정과 직접 확인으로 아래를 고쳤다. **가장 중요한 것부터:**

1. **Plan A 의 시장 라벨 오염 — 측정 대상이 조용히 바뀌던 경로.**
   Plan A 는 시가총액을 `market="ALL"` 한 번에 받지만 시장구분은 시장별로 3회를 따로 물어야
   한다(`get_market_cap_by_ticker` 가 `MKT_ID` 컬럼을 떨어뜨린다). 그 3회 중 하나가 빈 응답이면
   그 시장 종목이 통째로 무라벨이 되고, 예전 코드는 `mkt != "KNX"` 로 걸러서 **무라벨을
   KOSPI+KOSDAQ 에 포함**했다. KONEX 는 시총이 가장 작은 집단이라 그대로 '시총 하위
   1,000종목'을 점유한다 — 판정표는 `KONEX 제외`라고 적힌 채 다른 유니버스를 측정하게 된다.
   더 나쁜 건 pykrx 1.2.8 의 `dataframe_empty_handler` 가 예외를 삼키고 빈 값을 돌려주므로
   **경고조차 뜨지 않는다**는 점이다. 지금은 (a) 시장별 목록이 하나라도 비면 그 날짜를 쓰지
   않고, (b) 무라벨 종목은 '모른다'로 보아 전 상장사에서 제외한다(보간하지 않는다).
2. **오류 응답이 영구 결측으로 굳던 경로.** `000`/`013` 이 아닌 status(예: `100`·`101`·`901`)도
   캐시에 저장돼, 다음 실행의 인벤토리 스캔이 파일 존재만 보고 '보유'로 판정했다. 이제
   확정된 사실(`000`/`013`)만 캐시한다.
3. **3단 실패인데 지난 실행의 캐시로 조용히 진행하던 경로.** §2.4 는 3단 실패 시 전 스냅샷
   `UNVERIFIED` 를 요구한다. 이제 캐시가 있어도 쓰지 않고, 캐시가 있다는 사실은 로그에 남긴다.
4. **죽은 키가 하루치 예산을 태우던 경로.** `010`(등록되지 않은 키)은 재시도 대상도 halt
   대상도 아니라서 서킷 카운터를 오히려 리셋했다. 이제 즉시 중단하고, 재시도·halt 어디에도
   안 걸리는 status 가 연속 200건이면 방지턱이 작동한다.
5. **HTTP 200 인데 JSON 이 아닌 응답**(점검 안내·차단 페이지)이 `미분류 → 코드로 해결 불가`로
   분류되어 수집 전체를 막았다. 연결은 도달했으므로 '해결 가능'으로 분류한다.
6. **Plan B 가 로그인 필드명을 못 읽었을 때 `KeyError` 로 실행 전체가 죽던 경로.** 이제
   추측으로 채우지 않고 로그인만 건너뛰어 비로그인 경로로 넘어간다.
7. **종가 캐시가 포맷에 눈이 멀어 있던 문제.** 메타(json)만 보고 커버리지를 판정해서, pyarrow
   가 빠진 환경에서는 예전 parquet 캐시를 '있다'고 믿고 읽지는 못해 전 종목 종가가 조용히
   사라질 수 있었다. 이제 데이터 파일 존재까지 확인하고 parquet·csv 를 모두 후보로 읽는다.
   parquet 저장도 원자적으로 바꿔 반쪽 파일이 남지 않게 했다.
8. **§5.1 준수.** 레코드가 있는데 PIT 폐기가 0건인 스냅샷이 있으면 계약 위반으로 중단한다.
   다만 **산출물을 전부 남긴 뒤에** 중단한다 — 증거 없이 죽으면 다음 실행의 출발점이 사라진다.
9. pykrx 호출도 KRX 게이트를 통과한다(§8 의 '단일 스레드 + 1초'가 절반만 지켜지고 있었다),
   `Ctrl-C`/`SystemExit` 는 넓은 `except` 에서도 그대로 올라간다(수천 콜짜리 실행을 멈출 수
   있어야 한다), ENOSPC 는 워커 안에서도 삼켜지지 않는다, 예산은 250콜마다 저장한다,
   DART 연결 진단을 corpCode 수신보다 먼저 돌려 진단물이 반드시 남게 했다,
   Plan C 의 발행주식총수 필드는 종목 단위로 집계해 폴백 건수를 판정표에 남긴다.

나머지 제기분은 반증으로 기각했다(대부분 예외 계층·게이트 의미·`_gate(unverified=)` 의
용도를 다르게 읽은 것이었다).
